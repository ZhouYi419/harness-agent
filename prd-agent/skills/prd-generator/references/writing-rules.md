# PRD 写作规则

## 目标与范围

- 背景描述现状和问题，不预设解决方案。
- 产品目标描述用户或业务结果，避免“提升体验”等无法验证的空话。
- 范围内只包含已确认属于 MVP 的能力；范围外记录用户明确排除或明确延期的内容。
- 如果成功指标未确认，放入待确认事项，不给出臆测数字。

## 用户场景与流程

- 场景应包含用户、触发情境、动作和期望结果。
- 核心流程从用户可感知的起点写到完成条件；分支只保留会改变功能或规则的节点。
- 不把页面布局、技术实现或接口设计当成用户流程，除非用户明确要求这些约束。

## 功能拆解

- 模块按同一业务目标或流程阶段聚合；子功能应可单独描述和验收。
- 每项功能使用稳定的 `FR-nnn` ID，并说明使用者、前置条件、触发、主流程和完成结果。
- 避免把多个互不依赖的行为塞进一个功能；也不要把每个按钮机械拆成独立功能。
- 通过 ID 关联规则、异常和验收标准，避免在多处复制同一约束。

## 业务规则

- 每条 `BR-nnn` 只表达一个条件和确定结果，说明适用的功能。
- 使用“当……时，系统必须……”等可判断表述，避免“合理”“尽快”“通常”等模糊词。
- 价格、权限、审批、状态、数据归属、通知条件、补偿机制和阈值必须有用户依据；没有依据就进入待确认事项。

## 异常场景

- 每条 `EX-nnn` 包含触发条件、系统行为、用户可见反馈和可恢复路径。
- 至少覆盖已知的输入无效、权限不足、重复操作、依赖失败或状态冲突，但只写与当前产品实际有关的类别。
- 不用“系统报错”结束描述；说明是否保留数据、能否重试以及下一步是什么。

## 验收标准

- 每个 MVP 子功能至少有一个主流程验收场景；关键异常需要独立验收场景。
- 每条 `AC-nnn` 使用 Given/When/Then：Given 是可建立的前置状态，When 是单一动作，Then 是可观察结果。
- 避免把内部实现、函数调用或数据库字段作为验收结果，除非 PRD 本身面向对应技术接口。
- 验收标准不得包含待确认规则；规则未确认时写入待确认事项并说明阻塞哪些 AC。

## 表达与一致性

- 术语首次出现时给出清晰定义，并在全文保持同一名称。
- 使用“必须”表示硬性规则，“可以”表示允许行为，“建议”只能出现在 Agent 建议章节。
- 删除重复描述；当两处内容冲突时，以用户最新明确确认的内容为准，并同步所有引用位置。
