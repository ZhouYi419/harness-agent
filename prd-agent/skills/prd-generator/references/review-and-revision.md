# PRD Review 与修订规则

## Review 模式

默认只输出 Review 报告，不修改源文档。按以下顺序检查：

1. **完整性**：目标、用户、范围、流程、功能、规则、异常和验收是否覆盖 MVP。
2. **一致性**：术语、范围、功能、规则、异常和验收之间是否矛盾或失去引用。
3. **明确性**：是否存在多种合理解释、未定义角色、未知状态或模糊阈值。
4. **可测试性**：验收条件是否可建立、可执行、可观察，是否覆盖关键异常。
5. **风险**：是否擅自确定权限、价格、审批、数据归属、合规或失败补偿。

报告格式：

```markdown
# PRD Review 报告

## 总体结论

## 问题清单

| ID | 严重度 | 类别 | 位置 | 问题与影响 | 建议处理 |
| --- | --- | --- | --- | --- | --- |
| RV-001 | 阻塞 / 重要 / 一般 | 完整性等 | ... | ... | ... |

## 待用户确认

## 做得清楚的部分
```

- “阻塞”表示无法可靠实现或验收核心 MVP；“重要”表示可能造成明显返工；“一般”表示不会阻断交付的质量问题。
- 不报告纯个人风格偏好。每项问题必须指出位置、影响和可执行的处理建议。
- 如果用户只说“Review”，不要重写 PRD。用户明确要求“Review 并修复”时，先报告阻塞问题；不存在待确认的阻塞问题后再进入修订模式。

## 修订模式

1. 如果目标是文件，先读取完整原文；如果 PRD 仅在对话中，使用最近一版完整 PRD。
2. 把每条反馈映射到受影响的 FR、BR、EX、AC 和章节。反馈含糊、互相冲突或改变关键规则时，返回 `requirement-clarification`，不得先改。
3. 保留不受影响的内容和 ID。同步更新所有交叉引用；新增 ID 只追加，已删除 ID 不复用。
4. 输出或写入修订后的完整 PRD，删除已经被明确否定的内容，不保留正文变更日志。
5. 完成后用聊天摘要列出：本次修改、未修改的关键范围、仍待确认事项；如果写入文件，同时给出路径。

不得用“其他内容不变”代替完整修订稿，也不得只输出 diff 让用户自行拼接。
