# 需求澄清门禁

在加载 `prd-generator` 或修改 PRD 文件之前执行本 Skill。目标不是让所有信息都完美，而是阻止关键业务事实被猜测。

## 先识别任务模式

- **创建**：用户提供产品想法，要求生成新的 PRD。
- **Review**：用户要求检查已有 PRD。只要评审对象可获得且评审范围没有重大歧义，就直接评审；文档缺口是评审发现，不是阻塞问题。
- **修订**：用户提供反馈，要求更新对话中的 PRD 或指定文件。

如果任务模式、评审对象或要修改的目标文档无法确定，先询问用户。

## 建立事实账本

分析信息时，把每条内容归入以下一种状态。不要混淆这些状态：

- **用户已明确**：来自用户当前或先前的直接陈述。
- **用户已确认**：Agent 曾提出选项或问题，用户已经作答。
- **待确认**：尚无可靠答案，但不会阻断当前工作的非关键缺口。
- **Agent 建议**：可供用户选择的方案，不是需求事实。

在最终 PRD 中，前两类可以写入正式需求；第三类进入“待确认事项”；第四类只能进入“Agent 建议”。

## 完整性检查

创建 PRD 时检查：

1. 产品要解决的问题和产品目标。
2. 目标用户或主要参与者。
3. 至少一个核心使用场景和用户期望结果。
4. MVP 范围，以及明确已知的范围外内容。
5. 核心流程的起点、关键动作和完成条件。
6. 会改变流程结果的业务规则。
7. 涉及账号、角色、审批、敏感数据或所有权时的权限与数据边界。
8. 可判断 MVP 是否成功的验收目标或成功信号。

前四项缺失通常是关键缺口。第 5 至 8 项只有在对应能力确实存在且会影响核心流程时才是关键缺口；不要为了填模板而发明问题。

以下规则不得自行补充：价格和计费、角色权限、审批关系、状态流转、数据归属与保留、合规要求、通知触发条件、失败补偿、关键阈值。

修订 PRD 时，以下情况会阻塞修改：

- 反馈指向多个可能的模块或功能，无法判断修改位置。
- 新反馈与已有已确认需求冲突。
- 反馈会改变上述关键业务规则，但没有给出替代规则。
- 用户要求更新文件，但没有可确定的工作区内目标路径或现有内容。

## 提问规则

- 一轮最多提出 5 个会改变 PRD 内容的高价值问题；合并同类问题。
- 优先使用 `ask_user_question` 提供 2 至 3 个真实可选方案，并把推荐项放在首位；无法合理枚举时再用自由回答。
- 问题应说明需要决定什么，不要询问可从已有 PRD 或对话中读取的事实。
- 提问后立即停止本轮：不生成正式 PRD，不写文件，不修改旧 PRD。
- 用户回答后重新执行本门禁；仍有关键缺口时可以再问一轮。

## 放行结果

关键缺口全部解决后，加载 `prd-generator` 继续。非关键缺口不阻塞，但必须以明确、可回答的问题进入“待确认事项”。如果没有待确认项，写“无”。
