# 澄清问题策略

在 `analyze_requirement` 产生 Requirement Context 后使用本 Skill。

目标是解决会阻塞 PRD 的关键问题，不是一次性补齐所有可能信息。

## 必须询问

以下问题必须询问，不得使用默认值替代：

- 产品目标、主要用户、核心场景或 MVP 范围缺失。
- 两条需求不能同时成立。
- 权限、审批、状态流转、计费、数据归属或合规规则会改变核心流程。
- 一个模糊描述存在多个差异明显的合理解释。
- 缺失信息会导致功能无法实现或验收。

## 可以暂缓

以下内容通常可以保留在待确认项或 Agent 建议中：

- 不影响核心流程的文案。
- 非关键页面布局。
- 尚未要求的增强功能。
- 不影响 MVP 验收的技术实现偏好。
- 可在后续设计阶段确定的视觉细节。

可以暂缓不等于可以冒充用户确认。默认方案必须进入 `assumptions` 或 `suggestions`。

## 排序规则

按以下顺序排序：

1. 冲突需求。
2. 产品目标、主要用户、核心场景和 MVP 范围。
3. 权限、状态、价格、数据和失败处理规则。
4. 会影响多个模块的问题。
5. 只影响单个 Feature 的问题。
6. 非阻塞优化项。

同一优先级下，优先询问能一次消除多个缺口的问题。

## 数量限制

- 一轮最多询问 5 个问题。
- 每个问题只要求用户做一个主要决定。
- 相同主题的问题可以合并，但不能把多个无关决定塞进同一道题。
- 第一轮只询问 critical 和 high 问题。
- 第一轮回答后重新分析，再决定是否需要第二轮。
- 不要一次列出几十个问题。

## 问题形式

能够合理枚举时，提供 2 至 3 个互斥选项。

如果存在明显推荐方案：

- 推荐项放在第一位。
- label 以 `(Recommended)` 结尾。
- description 说明该选项的实际影响。

不能合理枚举时允许自由回答，不要提供虚假的固定选项。

完成排序后调用 `ask_requirement_questions`。用户回答返回后调用 `apply_requirement_answers`，不得手工拼接答案并跳过 Requirement Context 更新。
